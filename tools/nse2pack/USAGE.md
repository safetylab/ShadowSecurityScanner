# Converting Nmap NSE scripts into check-packs

`nse2pack` reads a directory of Nmap NSE scripts and writes **check-packs** —
JSON files that ShadowSecurityScanner loads at startup and runs alongside its
built-in checks. It also writes a report naming every script it could **not**
translate, and why.

A check-pack is data, not code. It executes nothing, so the scanner accepts it
without a signature and without an operator consent prompt. The format
describes one thing: *exchange something with the target and look at the
reply*. There are no variables, branches or loops in it, which is why a good
part of any NSE corpus will not convert — that is a boundary of the format, not
a gap in this tool.

## What you need

* **ShadowSecurityScanner** itself — download the build for your platform from
  the [releases page](https://github.com/safetylab/ShadowSecurityScanner/releases/latest).
  Nothing has to be built.
* **Python 3.9 or newer** for this tool. No third-party packages, no network
  access, nothing to install.
* **The NSE script you want**, or a whole directory of them — for instance the
  `scripts/` directory of an Nmap installation.

The whole route is four commands and a restart:

```bash
./nse2checkpack /usr/share/nmap/scripts/http-git.nse -o out   # 1. convert
./nse2checkpack --check -v out/*.json                         # 2. inspect
cp out/*.json "<the probes folder the app shows you>"          # 3. install
#                                                              4. restart the app and scan
```

## Quick start

One script, start to finish:

```bash
cd tools/nse2pack
./nse2checkpack /usr/share/nmap/scripts/http-server-header.nse -o out
```

Or a whole corpus at once:

```bash
./nse2checkpack /usr/share/nmap/scripts -o out --source nse
```

```
  nse-discovery.json           pack-nse-discovery — 2 checks (sweep: 0, own row: 2)
  nse-version.json             pack-nse-version — 3 checks (sweep: 1, own row: 2)
  nse-vuln.json                pack-nse-vuln — 1 check (sweep: 1, own row: 0)

  scripts read:   11
  converted:      6
  not converted:  5 (exploitation: 2, routing: 1, untranslatable pattern: 1, weak assertions: 1)
```

The run leaves this in `out/`:

| file | what it is |
|---|---|
| `nse-<category>.json` | one check-pack per NSE category: one catalogue row the operator can switch on and off |
| `report.md` | what converted, what did not, and why — read this one |
| `report.json` | the same report for scripts and CI |

Nothing is ever written outside the output directory, and the input scripts are
read as data: they are parsed, never executed.

## The whole workflow

### 1. Convert

```bash
./nse2checkpack /usr/share/nmap/scripts -o out --source my-feed
```

Pick `--source` carefully. It travels with every finding the pack produces, it
is the name an operator sees beside the result, and it is the switch that turns
the whole set off. The folder a pack happens to live in says only *where* it
was found; the pack says *whose* it is.

### 2. Inspect the pack

```bash
./nse2checkpack --check out/nse-version.json             # accepted, dropped, and why
./nse2checkpack --check -v out/nse-version.json          # plus the plan of each check
./nse2checkpack --check --strict out/*.json              # non-zero exit on any drop
```

```
out/nse-version.json
  source:   nse (version 1, api 1)
  plugin:   pack-nse-version — 'NSE version checks (converted)'
  checks:   3 accepted, 0 dropped
  runs as:  1 check(s) inside the web sweep (catalog row "cgi"), 2 under this pack's own row 'pack-nse-version'
  acarsd-info
    when service acarsd and ports 2202 and any of 2202 open → tcp banner → 2 assertion(s) → detect acarsd + version
    own row: it is not an HTTP check
```

`--check` applies the same refusal rules the scanner's compiler applies (§5 of
the format specification) and the same routing rule (§7), so it tells you what
the scanner will do with the file before you install it. Use it on packs you
edited by hand as well — a pack is plain JSON and is meant to be edited.

Checks generated by this tool pass these rules before they are written, so a
clean run is the expected outcome rather than a pleasant surprise. If `--check`
does drop a generated check, that is a defect in the converter — see *Reporting
a problem* at the end.

The desktop application ships its own compiler, which is the authority; this
mode is a faithful reimplementation of the published rules, calibrated against
the reference packs in the repository.

### 3. Install

Two ways, both without a signature, because a pack executes nothing:

* **Your own folder.** Settings → Sources → Add source → *A folder of my own*,
  then give an absolute path. Every `*.json` directly in that folder is read.
  Subdirectories are not walked.
* **The scanner's data directory.** Drop the files into `<data>/probes/`. The
  path is shown in the same panel.

**Packs are read once, at startup.** A scanner that is already running will not
pick up a new file. Restart it.

### 4. Scan something you are allowed to scan

A pack that compiles is not yet a pack that works. Point the scanner at a host
running the service the check is about and confirm two things: that the finding
appears where it should, and — more easily forgotten — that it stays absent
everywhere else. A reference service you control is the right target for this.

### 5. Read the report before you trust the coverage

A pack that converted 40 of 300 scripts and a pack that converted 300 of 300
look identical from the outside. `report.md` is what tells them apart, so treat
it as part of the output rather than as a log.

## Command-line reference

| option | meaning |
|---|---|
| `scripts…` | one or more directories (walked recursively for `*.nse`) or individual script files |
| `-o`, `--out DIR` | where packs and reports are written (default `out`) |
| `--source NAME` | the `source` field: the name users see and switch off (default `nse`) |
| `--pack-version N` | the pack's `version` stamp; a higher number replaces a lower one on the installed side (default `1`) |
| `--single` | write one pack instead of splitting by NSE category |
| `--products FILE` | JSON map from the product string in NSE to its canonical spelling in the scanner's database |
| `--min-marker N` | how long a lone piece of evidence must be before a check is trusted (default `8`) |
| `--strict` | exit non-zero if any generated check failed the compiler rules — put this in CI |
| `--quiet` | no terminal summary; the reports are still written |
| `--check` | do not convert: inspect packs that already exist and report what the scanner will accept, drop and why |
| `-v`, `--verbose` | with `--check`, print the plan of each accepted check |

Exit codes: `0` success, `1` a generation error (with `--strict`), a pack that
failed validation, or — under `--check` — a refused pack, `2` nothing to read at
the given paths.

## Reading the report

`report.md` has three parts: the packs that were written, the scripts that were
refused grouped by class, and the scripts that converted with the check id each
one became.

### Refusal classes

The report groups refusals by cause.

| class | what it means | what to do |
|---|---|---|
| `exploitation` | the `brute`, `exploit`, `dos`, `malware` or `fuzzer` category, a request that changes state, or a method a declarative check may not use | Nothing. The format observes and never attacks; this is deliberate. |
| `logic` | a computed path or payload, three or more requests, two unrelated requests | Candidate for the scanner's second-level SDK, where a script subprocess may run real code. |
| `state` | no `action`, no exchange with the target, or a request to an arbitrary URL | Usually not worth porting. A pack may only talk to the target being scanned. |
| `routing` | a `hostrule` with no `portrule`, or a `portrule` the parser did not recognise | Check whether the script is tied to a service at all. If it is, and the rule is an unusual shape, that is worth reporting. |
| `untranslatable pattern` | `%b`, `%f`, a position capture or a back-reference, none of which exist in RE2 | Nothing automatic. Rewriting the pattern by hand is sometimes possible; the report quotes the exact pattern. |
| `weak assertions` | nothing could be asserted about the reply, or the only evidence is shorter than `--min-marker` with no product anchor | Consider `--min-marker`, below, but read the warning there first. |
| `generation error` | the check was built but then failed the compiler's own rules | A bug in this converter. `--strict` turns it into a failed build. |

An entry marked *candidate for a second-level script* is something this format
cannot express but the scanner's script SDK can: real code, signed, run with
explicit operator consent.

### Converted checks

Each converted script becomes one check, and the table names the route it took:

* **web sweep**. A single `GET` of a single path joins the
  shared CGI sweep, which fetches each distinct path once per endpoint and
  compares that one reply against every check referencing it. A thousand checks
  on one path cost one request. The trade is that they share the catalogue row
  `cgi`, and findings carry the "built-in" origin badge rather than your source
  name. The sweep's `disabled_sources` setting switches them off by your
  `source`.
* **own row**. Everything else — a byte transport, several
  steps, a method other than `GET` — gets a catalogue row of its own, named by
  the pack, with its own toggle, settings and origin badge.

## Getting more out of a corpus

### Map product names to your database

The most valuable thing a converted check can produce is not a finding but a
`detect`: the product and version it saw. The scanner then supplies the known
CVEs for that version, their EPSS scores, CISA KEV marks and the end-of-life
record. One reliable version extraction beats twenty checks asserting that a
page exists.

For that to work, `detect.product` has to match the canonical spelling in the
scanner's database. The converter takes whatever string the NSE script assigned
to `port.version.product`, lowercased. Where that differs from your database,
supply a map:

```json
{
  "Apache httpd": "apache",
  "OpenSSH": "openssh",
  "Microsoft IIS httpd": "iis"
}
```

```bash
./nse2checkpack /usr/share/nmap/scripts -o out --products products.json
```

Grep the generated packs for `"product"` once after a large run and reconcile
the list; it is a one-off cost per corpus.

### Lower the evidence threshold — carefully

By default a check is refused when its only evidence is a literal shorter than
eight characters and nothing anchors it. This is the rule that keeps an
imported pack from flooding an operator with false positives: a marker like
`login` matches a large share of the web.

```bash
./nse2checkpack scripts -o out --min-marker 5
```

will convert more scripts, including ones that match far too much. If you lower
it, run the result against a few hosts you know are clean and see what fires
before you ship it. A pack that cries wolf discredits every check in it,
including the good ones.

A short marker is accepted without lowering the threshold when something else
narrows the check: a second piece of evidence, a product anchor, a header test,
a captured value, a second step, or a byte exchange on a specific port.

### One pack or many

By default the output is split by NSE category, because one pack is one
catalogue row: an operator can enable `version` checks and leave `vuln` ones
off. `--single` collapses everything into one row instead, which is simpler to
distribute and coarser to control.

## Updating a pack later

Re-run the converter on a newer script corpus and bump the stamp:

```bash
./nse2checkpack /usr/share/nmap/scripts -o out --source my-feed --pack-version 2
```

Two properties make this safe. Check ids are derived from the script filename,
so a regenerated pack **updates** the checks already installed instead of
duplicating them. And the scanner replaces an installed pack only with a higher
`version`, so the number must go up whenever the content changes.

If the same source previously produced findings for users, consider carrying
the old `fingerprint` values across: findings with a matching fingerprint are
deduplicated between scans rather than resurfacing as new ones after the
migration. The converter does not set `fingerprint`; add it where you know what
the previous value was.

## In continuous integration

```bash
set -e
./nse2checkpack "$NSE_DIR" -o out --source my-feed --pack-version "$BUILD" --strict
./nse2checkpack --check --strict $(ls out/*.json | grep -v report.json)
```

The first `--strict` fails the build when a generated check does not satisfy the
compiler rules; the second re-reads the written files and fails on anything the
scanner would drop. Together they mean a regression in generation surfaces at
build time rather than in a user's startup log.

The output is deterministic: the same corpus produces byte-identical packs, so
committing them and diffing between runs is a reasonable way to review what a
corpus update actually changed.

## What the converter will never do

These are deliberate, and knowing them saves you looking for a flag:

* **It never claims `verified: true`.** That field asserts that vulnerable
  behaviour was *observed*, not inferred from a version string. Distributions
  backport fixes without changing version numbers, so a version match means
  "possibly affected". The scanner derives the confidence itself from how
  specific the match was.
* **It never invents a severity.** A `vuln` script becomes `medium`, everything
  else `info`. If a finding deserves more, raise it deliberately.
* **It never emits a request that changes state.** No `PUT`, `DELETE`, `PATCH`
  or `CONNECT`, and no `POST` either, since the format has no documented field
  for a request body.
* **It never addresses anything but the target** being scanned.

A script that needs any of those is not a pack. It is either a candidate for
the script SDK — where code runs, signed and with explicit consent — or
something not worth porting.

## Troubleshooting

**Almost nothing converted.** Expected for a general NSE corpus: much of it is
Lua logic rather than request-and-match. Read the refusal classes in
`report.md` — if `logic` dominates, that is the format's boundary; if
`routing` dominates, the scripts may use a `portrule` shape worth adding
support for.

**A finding shows "built-in" instead of my source name.** The check is a single
`GET` and runs inside the shared CGI sweep, which owns the catalogue row. That
is routing, not an error. The report's route column tells you in advance which
checks this applies to.

**The scanner did not pick up my pack.** Packs are read once, at startup —
restart it. Check that the file sits *directly* in the configured folder;
subdirectories are not walked. Then confirm the pack loaded: the startup log
names any check that failed to compile, grouped by reason, and the pack's
catalogue row carries the accepted count, so a pack that half-loaded says so
rather than looking complete.

**A check fires on hosts that are not affected.** Look at its `expect` in the
pack. If it rests on one short literal, it is exactly what `--min-marker`
guards against; raise the threshold, or edit the check to add a
`require_ci` product anchor. Packs are plain JSON and are meant to be edited.

**A check this tool wrote was dropped.** Whether it was `--check` or the
scanner's startup log that said so, that is a converter bug rather than a format
quirk: every check is validated against the same rules before it is written.
Please report it with the NSE script and the message that was printed.
